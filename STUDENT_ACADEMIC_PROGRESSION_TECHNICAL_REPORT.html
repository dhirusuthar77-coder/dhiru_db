The supplied project report describes a layered three-tier architecture.

Business & Integration Engine Credit-weighted SGPA = Σ(Credits × Grade Point) / Σ(Credits); cumulative CGPA across active semesters; drop-year chronology detection and validation alerts; event-driven sync queue and payload snapshot dispatcher.

Method C: Python / CLI Database Administration

For programmatic changes, connect to SQLite, enable foreign keys, perform the update inside a transaction, commit on success, roll back on an IntegrityError, and close the connection.

Step Example
Connect sqlite3.connect('database/student_progression.db')
Enable foreign keys conn.execute("PRAGMA foreign_keys = ON;")
Update UPDATE students SET branch = 'Electronics & Telecommunication', email = 'arjun.reddy@viva-technology.org' WHERE roll_number = '23FC003';
Successful update Commit the transaction and report success.
Constraint violation Catch sqlite3.IntegrityError, roll back, and report the integrity violation.
Close Close the database connection in a finally block.

4. Schema Constraints & Violation Handling

The following table reproduces the constraints and violation-handling rules stated in the supplied source report.

Constraint Type Target Entity / Column Rule Enforced Violation Handling
PRIMARY KEY All 8 tables (student_id, semester_id, etc.) Auto-incrementing integer keys guarantee entity uniqueness. SQLITE_CONSTRAINT_PRIMARYKEY; normally prevented by auto-generation; form alerts if manually overridden.
UNIQUE candidate key students(roll_number) No duplicate roll numbers across departments. SQLITE_CONSTRAINT_UNIQUE; form reports that the roll number already exists.
UNIQUE candidate key students(email) No duplicate institutional email addresses. SQLITE_CONSTRAINT_UNIQUE; form reports that the email is already registered.
UNIQUE composite key school_records(student_id, qualification_type) At most one 10th and one 12th/Diploma record per student. SQLITE_CONSTRAINT_UNIQUE; existing record is updated rather than duplicated.
UNIQUE composite key semesters(student_id, semester_number) Each semester number (1–8) can be registered once per student. SQLITE_CONSTRAINT_UNIQUE; existing semester record is loaded.
CHECK school_records(percentage) Percentage must be between 0 and 100. SQLITE_CONSTRAINT_CHECK; invalid value is rejected and UI displays a validation alert.
CHECK semesters(sgpa), semesters(cgpa) GPA must be within 0–10. SQLITE_CONSTRAINT_CHECK; invalid grade-point values are blocked.
CHECK drop_years(start_year, end_year) end_year >= start_year. SQLITE_CONSTRAINT_CHECK; invalid chronology is rejected.
CHECK semester_results(internal_marks, external_marks) Marks must be between 0 and 100. SQLITE_CONSTRAINT_CHECK; out-of-range marks are blocked.
FOREIGN KEY — CASCADE students → school_records, semesters, drop_years, achievements Deleting a student removes dependent child records. Automatic cascade in a transaction; avoids orphan records.

5. Third Normal Form (3NF) Rationale

The source report states that for every non-trivial functional dependency X → Y, X must be a superkey, or every attribute in Y \ X must be a prime attribute (part of a candidate key).

Relation Attributes / Keys 3NF Rationale
students student_id (PK), roll_number (candidate key), full_name, email (candidate key), phone, branch, admission_year, current_status. Functional dependencies: student_id → all attributes; roll_number → all attributes. Attributes are atomic (1NF); keys are non-composite; no non-prime attribute determines another non-prime attribute (3NF).
semesters semester_id (PK), student_id (FK), semester_number, academic_year, sgpa, cgpa, result_status. Candidate key: (student_id, semester_number). SGPA and status depend on the specific student and semester; the source states no transitive dependency between academic year and SGPA.
subjects subject_id (PK), subject_code (candidate key), subject_name, subject_type, credits, semester_number. An independent catalog reduces insertion, update, and deletion anomalies: courses can be added before enrollment; course details can be updated once; deleting results does not delete the catalog.
semester_results result_id (PK), semester_id (FK), subject_id (FK), internal_marks, external_marks, total_marks, credits, grade. Candidate key: (semester_id, subject_id). Grade depends on semester registration and subject; theory and practical marks are stored in separate atomic columns.
school_records school_record_id (PK), student_id (FK), qualification_type, board_name, school_name, passing_year, percentage. Candidate key: (student_id, qualification_type). Prior schooling records are stored independently; prevents repetitive null fields for students without separate diploma records.
drop_years gap_id (PK), student_id (FK), start_year, end_year, reason, description. Non-academic periods isolated from active semester evaluation tables; prevents dummy progression rows.
achievements entry_id (PK), student_id (FK), category_id (FK), title, organization, entry_date, certificate_url. Student portfolio activities maintained as atomic rows with foreign keys to standardized categories.
achievement_categories category_id (PK), category_name (candidate key), category_group, activity_type. Standardized catalog prevents repetitive strings and data redundancy across portfolio records.
